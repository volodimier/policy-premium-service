### What was delegated and what was not

The developer set the constraints and retained control of anything irreversible: the stack, the
workflow rules, repository visibility, the branch protection model, and every commit, push and
merge. Claude Code never ran `git commit` or `git push` at any point — those were done by hand,
one handoff per issue, from `CLAUDE.md` onwards. Access to the GitHub CLI was limited to issues
and pull requests.

Within those constraints, Claude Code handled implementation, verification and diagnosis, and
proposed decisions for approval rather than making them silently.

### Business rules: three defects that only appeared when implemented

The developer notes above that the proposed business rules were accepted without pushback. It is
worth recording what that cost, because those rules looked reasonable on paper and were not:

1. **The 500 000 band boundary was self-contradictory.** The table said `≤500k → 1.00` and
   `500k–1M → 1.15`, while the stated semantics said bands were inclusive-lower and
   exclusive-upper. Those disagree about exactly 500 000. The contradiction went unnoticed until
   code had to pick one.
2. **The minimum premium could never fire.** It was set at 500 SEK, but the cheapest premium the
   rate table can produce is 720 — every factor at its minimum still lands 44% above the floor.
   `minimumPremiumApplied` was dead code, and the acceptance criterion requiring it to be tested
   was unsatisfiable. The developer decided to raise the floor to 750, which makes it engage on
   exactly one combination: the bottom of the book.
3. **Rounding is never exercised.** Base rates are whole numbers and every factor a whole
   hundredth, so all 300 possible premiums terminate at or before two decimal places — `HALF_UP`
   never changes a value. Rather than churn the rates a second time, the test asserts what is
   genuinely exercised (every premium is returned at exactly scale 2), and the rounding mode is
   documented as defensive.

None of these were caught by reviewing the plan. All three surfaced from writing the code and
computing the actual extremes.

### Where Claude Code was wrong

- **Spring Boot 3.5.x was written into `CLAUDE.md` from memory.** No 3.x line exists any more;
  the current release is 4.1.0. Caught by querying Spring Initializr rather than trusting recall.
- **Maven was chosen by default rather than decided.** When the developer questioned it, there
  was no real justification — it was Initializr's default. Gradle was the better fit here, since
  Checkstyle and JaCoCo are core plugins.
- **springdoc compatibility was called a risk twice, and was wrong both times.** It was flagged
  as likely incompatible with Spring 7 at the start, and again before implementation. It worked
  on the first attempt.
- **A Quality Monitor glob matched the wrong file.** `**/checkstyle/*.xml` matched
  `config/checkstyle/checkstyle.xml` — the ruleset, not a report — and grading aborted with a
  parse error. The pattern was plausible and passed YAML validation; only running it against a
  real filesystem exposed it.
- **A CI step hung.** The non-root property was verified locally with `docker exec` against a
  running container, but a *different* command was written into the workflow — `docker run image
  id -u` — and never dry-run. Because the image declares an `ENTRYPOINT`, those arguments were
  appended to it, so the step launched the application and hung until timeout.

### The recurring failure mode: green checks that proved nothing

The last two failures share a shape, which is arguably the most useful thing in this record.

The Quality Monitor job **reported success while posting nothing but a stack trace** — the action
exits 0 even when parsing aborts. The uid check was **testing a property that was true** (the
container does run as uid 100) using a command that could never have verified it.

In both cases the status was green, or green-adjacent, while the underlying verification was
worthless. Both were caught by reading what the job actually output rather than whether it
passed. Later pipeline changes were dry-run locally before being committed for this reason, and
the `--entrypoint` fix was confirmed by first demonstrating the broken command launching the
application.

### How the work was verified

Gradle could not run on the developer's machine at all — the daemon fails with
`Unable to establish loopback connection`, a `SocketException` inside `sun.nio.ch.PipeImpl`,
apparently local security software blocking loopback for the JVM. Plain Java loopback worked
fine, so the problem was specific to the daemon handshake.

Rather than modify the machine's security configuration, every build, test run and container
check in this session was executed inside Docker. This is also why the Dockerfile carries an
optional `--target test` stage: it allows anyone to build and verify from a clean clone without a
working local Gradle.

Nothing was reported as working merely because it compiled. The premium examples in the README,
the documented Swagger URLs, the byte-identical `POST`/`GET` response bodies and the image digest
promotion assertion were each checked against a running container before being written down.

### Changes that came from review rather than the plan

Three of the twelve issues did not exist when work started, and each came from the developer
questioning something:

- **Quality reporting on pull requests** — from noticing that a green check displayed no test or
  coverage numbers at all.
- **Folding CD into the CI pipeline** — from comparing the two-workflow design against a single
  visual pipeline. This also surfaced a genuine weakness: CD was *rebuilding* the image rather
  than promoting the tested one, which matters because the runtime stage upgrades OS packages, so
  a rebuild of the same commit can genuinely differ. The image is now exported and its digest
  asserted at deploy time.
- **Removing a redundant test** — from asking whether `POST` had integration coverage. It did,
  but the question exposed that the generated `contextLoads` test had become redundant and was
  costing an entire extra Spring context per build. Coverage was unchanged after deleting it,
  which is what proved it redundant.

### Where Claude Code pushed back

Not every proposal was accepted, and not every question implied a defect. Asked whether the
reporting job should gate the container build, Claude Code argued against it: the job is
report-only by design, so "code that failed the quality check" is not a reachable state, and
placing a third-party action with elevated permissions on the critical path would let a tooling
outage block delivery for reasons unrelated to code quality. The real gate — formatting, static
analysis and tests — already runs strictly before it.

Similarly, when auto-opening Swagger UI in a browser on startup was proposed, Claude Code flagged
that it would fail or hang inside a container and on CI runners, and the idea was dropped.
